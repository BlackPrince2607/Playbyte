1  Scope 
This document defines the implementation architecture for the Playbyte MVP: the mobile client, application API, 
PostgreSQL data model, realtime delivery, background processing, editorial CMS, authentication, privacy, sharing and 
media generation, notifications, observability, deployment, and the scaling path required by the PRD. 
It is written for the engineers building the system. Product rationale lives in the PRD; this document assumes that 
rationale and focuses on how the system is built, why each decision was made over the available alternatives, and 
what conditions would change it.

Playbyte has strong relational requirements — users, moments, responses, friendships and privacy settings are highly 
interdependent and benefit from transactional guarantees a single relational database gives for free. It also has one 
component with a genuinely different scaling shape: realtime fanout to up to 100,000 concurrent viewers. Splitting 
the system into services before that asymmetry is proven would trade a real, measurable cost (operational overhead 
for a small team) for a benefit that doesn't exist yet. 
The monolith is kept modular specifically so the realtime path can be extracted later without a rewrite: it sits behind a 
RealtimePublisher interface from day one, so Supabase Broadcast is a swappable implementation detail, not a 
structural assumption baked into the rest of the codebase. 
Decision rule.  Default to the boring, already-managed option (Supabase Postgres/Auth/Storage/Broadcast). Introduce 
new infrastructure only when a measured workload — not a hypothetical one — requires it. See Section 26.

Client-side button disabling is a UX nicety, not a correctness mechanism — it is never relied on to prevent duplicate 
responses. Uniqueness is enforced at the database boundary (one response per actor per moment), and retries reuse 
the same idempotency key, so a network retry after a timeout returns the existing result instead of creating a second 
row. 
9  Realtime Protocol 
Supabase Broadcast is the initial transport. Postgres Changes is deliberately not used for the high-fanout crowd 
stream — it ties realtime throughput directly to write-ahead-log replication, which does not hold up at 100K 
concurrent viewers on a single moment.

Snapshots are generated at a bounded cadence under load, and volumeState distinguishes a genuinely small crowd

misleadingly small number (Section 7.1.2). The system never sends one realtime message per individual response to 
every viewer; that pattern does not scale and is explicitly disallowed in Section 23. 
10  Feed Architecture 
The feed is server-ranked, cursor-paginated, and client-buffered. 
GET /v1/feed?cursor=<opaque>&limit=10 
 
Candidate order: 
  1. Live-now 
  2. Trending 
  3. Interest match 
  4. General/trending fallback 
 
Filters: not expired -> eligible for audience -> not blocked/restricted 
         -> not recently seen by this actor 
 
Client: renders current card, preloads next 3 
No ML at MVP.  The PRD calls for light personalization based on selected interest categories. Deterministic 
ranking is used instead of a model so behavior is explainable, cheap to operate, and testable — a hard 
requirement given the PRD's 500ms empty-state ceiling and the small initial editorial team producing 15–20 
moments/day.

Moments tagged health, tragedy, or election-related require an explicit second-approver state before LIVE — the

12  Authentication and Privacy 
● Registered identities are managed through Supabase Auth. 
● Guest sessions are first-class actors for MVP participation — this is what lets a new install reach a first 
moment without a signup gate. 
● Guest participation can be linked to a newly created user account, preserving response history on conversion. 
● The backend derives identity from the authenticated session; it never trusts a client-supplied user ID. 
● Response visibility is Public, Friends-only, or Private, set as an account default and overridable per moment. 
● Privacy checks run before returning friend presence or friend response data — never as a client-side filter. 
● Account deletion triggers a controlled workflow covering owned data, push tokens, friend relationships, and 
queued work. 
● Contact sync is opt-in and revocable; the raw address book is not retained as a permanent application 
dataset. 
Guest-to-Account Soft Prompt 
PRD Section 7.2.1 allows guest play with “a soft prompt to save progress after 3 moments,” but doesn't specify where 
that count lives. It is tracked server-side, not client-side, so the prompt fires consistently across app reinstalls and 
multiple devices within the same guest session's lifetime. 
● guest_sessions.moments_responded_count increments transactionally in the same write as each response 
insert (Section 8) — it cannot drift from the actual response count. 
● POST /v1/moments/:id/responses returns a promptAccountCreation flag once the count reaches 3; the client 
owns when and how to surface the prompt, never whether the threshold was met. 
● Dismissing the prompt does not reset the counter or suppress it permanently — the flag simply continues to 
be true on subsequent responses, and the client decides its own re-prompt cadence. 
● On conversion, guest_sessions.converted_user_id links the session and its full response history to the new 
account; no response data is duplicated or re-written. 
13  Sharing and Media Generation 
PRD Section 7.6 requires a branded, shareable result card generated in two taps, with native OS share-sheet 
integration and a deep link back into the specific moment. This was not modeled in the v1.0 architecture and is added 
here as its own module rather than folded into responses/, since it has a distinct dependency (image rendering) and a 
distinct failure mode (a slow render should never block the response flow that produced the result being shared).

Design constraint.  Card generation is synchronous but bounded — target under 1 second —

14  Notifications 
PRD Section 7.3 specifies three notification types, a default cap of 3/day, independent per-type opt-out, and a hard 
rule that nothing is sent for an expired or closed moment. The v1.0 architecture listed the push component but not 
the enforcement mechanism; it is specified here.

The daily cap and expiry check are enforced in the notification-delivery worker immediately before dispatch, using 
notification_deliveries as the count/dedupe source of truth — not at creation time, since a notification created hours 
before send can go stale by the time its slot comes up. Tapping any notification deep-links directly into the specific 
moment card.

17  Failure Handling 
Failure Behavior 
Realtime unavailable Retain last result, switch to bounded polling, reconnect later 
Response request timeout Retry with same idempotency key; check authoritative result first 
Duplicate response Return existing authoritative response / conflict semantics 
DB unavailable Fail the write safely; never claim a response succeeded 
Redis unavailable Continue from DB where safe; rebuild projections 
Worker failure Retry with backoff; dead-letter and alert after threshold 
Push provider failure Retry; record final delivery failure 
Storage failure Retry upload; never persist unusable asset metadata

23  Compliance and Data Regulation 
PRD Section 9.3 requires GDPR/CCPA-consistent handling, an age gate with no behavioral ad targeting below the 
regulated threshold, and opt-in/revocable contact sync. The v1.0 architecture stated the deletion and export 
requirement but did not model the underlying workflow; it is specified here. 
Requirement Implementation 
Data export User-initiated request creates a data_requests row; async worker assembles a portable 
export and delivers a signed, time-limited link 
Data deletion Same data_requests flow; deletion workflow from Section 12 executes owned data, push 
tokens, friendships, and queued work 
Age gate Enforced at signup on the auth module; unverified-age accounts are excluded from ad-
targeting eligibility flags used by sponsored-moment insertion (Section 24) 
Contact sync consent Stored as a revocable consent record, not inferred from possession of synced data; 
revocation triggers deletion of the raw address book 
Regional variance Consent and retention rules are read from a policy table keyed by region, not hard-coded, 
since GDPR/CCPA and future regimes diverge 
24  Non-Negotiable Engineering Rules 
1.  PostgreSQL is the source of truth.

2.  Do not perform privileged business writes directly from the mobile client. 
3.  Do not use Postgres Changes for the high-fanout moment crowd stream. 
4.  Do not broadcast raw response events to every viewer. 
5.  Use compact, versioned crowd snapshots. 
6.  Response creation is idempotent and protected by a database uniqueness constraint. 
7.  Realtime subscriptions are limited to active moments by default. 
8.  The client falls back to polling when realtime is unavailable. 
9.  All authorization is enforced server-side. 
10.  Every asynchronous side effect is retry-safe. 
11.  Any new infrastructure service requires an architecture decision record. 
12.  Do not introduce a second database until a concrete workload justifies it. 
13.  Load test the actual Playbyte traffic model before declaring capacity.

26  Final Recommendation 
Use Supabase as the starting platform. Keep PostgreSQL, Auth and Storage on Supabase. Use Supabase Broadcast for 
the first realtime implementation, but hide it behind a Playbyte realtime interface. Keep all product and authorization 
logic in the NestJS modular monolith. Add Redis and queue capacity based on measured load. When realtime scale or 
economics justify it, replace only that layer — potentially with AppSync, Ably, or a custom service.
